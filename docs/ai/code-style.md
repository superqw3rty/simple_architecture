# Стиль кода

Стили (SCSS, токены, брейкпоинты) — `styles.md`. Доступность — `accessibility.md`.

## Лимит 120 строк

Любой файл в `src/` — не больше 120 строк кода (пустые строки и комментарии не считаются). Для TS/TSX это проверяет ESLint (`max-lines`), для SCSS — `pnpm check:arch`. Ориентир для хорошего файла — около 70 строк.

Зачем: файл должен читаться как оглавление книги — набор понятных абстракций, детали которых спрятаны в соседних файлах.

Когда файл растёт, **не сжимай** код (однострочники, короткие имена, удаление пустых строк), а раздели по смыслу:

| Что разрослось | Как делить |
|---|---|
| View | выдели блок JSX в дочерний компонент `Child/` в папке родителя |
| Презентер | выдели связанную группу состояния и эффектов в хук `useSomething.ts` |
| Хук | выдели чистые вычисления в функцию `utils/doSomething.ts` |
| Чистая функция / модуль | раздели по ответственности, общий тип — в `types.ts` |
| SCSS | это сигнал, что view пора делить на дочерние компоненты |
| Тест | раздели по тестируемым сценариям: `name.cache.test.ts` |

Делить нужно по смысловым границам, а не «первые 100 строк / остальное». У каждого нового файла должно быть имя, объясняющее его содержимое без открытия.

## Форматирование

- Форматирует Prettier (`.prettierrc.json`): одинарные кавычки, ширина 100, висячие запятые. Руками формат не правим: `pnpm format`. `pnpm check` падает на неотформатированном коде.
- **Тело `if` / `else` / `for` / `while` всегда в фигурных скобках и на отдельной строке**, даже если это одна инструкция (ESLint `curly: all`, чинится `eslint --fix`).

```ts
// ❌
if (value !== undefined) search.set(name, String(value));

// ✅
if (value !== undefined) {
  search.set(name, String(value));
}
```

Скобки не дают потерять вторую строку при правке, а лимит в 120 строк не повод их экономить — повод разделить файл.

## Именование

- Компоненты и их папки — `PascalCase`; хуки — `useCamelCase`; функции и переменные — `camelCase`; константы модуля — `UPPER_SNAKE_CASE`.
- Файл называется так же, как его главный экспорт: `formatPageRange.ts` → `formatPageRange`.
- Булевы — `is*`, `has*`, `can*`, `should*`. Обработчики — `on*` и в пропсах, и в презентере: презентер отдаёт view обработчик под тем же именем, без переименования `handleX → onX` (D-51).
- Пропсы компонента — интерфейс `ComponentNameProps` в файле view (или в `types.ts`, если нужен ещё кому-то).
- Без сокращений: `button`, `event`, `index`, а не `btn`, `e`, `i` (исключение — общепринятые `id`, `url`, `dto`).

## TypeScript

- `strict` + `noUncheckedIndexedAccess`. Без `any`; `unknown` + сужение типа. `as` — только на границе с внешним миром (ответ сервера, DOM).
- Импорт типов — `import type { ... }` / `import { type X }`.
- Состояния с вариантами — дискриминируемые объединения, а не набор независимых булевых флагов.
- **У каждой функции явный возвращаемый тип**: презентеры, хуки, `utils/`, `api/`, хелперы в тестах; ничего не возвращает — `: void`. Без аннотации — только функция, тип которой задан контекстом: колбэк-аргумент (`items.map((item) => …)`, `it('…', () => …)`), значение типизированной переменной или свойства (`const Name: FC<NameProps> = …`, обработчик в объекте с объявленным типом результата). Проверяет ESLint (`explicit-function-return-type`), D-40.
- Результат хука — `interface UseNameResult` в файле хука; нужен ещё кому-то — в `types.ts` папки.
- Почему: выведенный тип виден только человеку при наведении. Явный тип — контракт: правка реализации, которая его ломает, даёт ошибку в самой функции, а не у потребителей.

```ts
// ✅ src/ShowsExplorer/useShowsExplorer.ts
interface UseShowsExplorerResult {
  isCompact: boolean;
  query: string;
  term: string;
  onQueryChange: (query: string) => void;
  inputRef: RefObject<HTMLInputElement | null>;
}

export function useShowsExplorer(): UseShowsExplorerResult { … }
```

- Только именованные экспорты.

## React

- Только функциональные компоненты, объявление через стрелку с типом `FC`: `export const Name: FC<NameProps> = (props) => …` (D-28). Хуки и обычные функции объявляются как удобно.
- Производные данные вычисляются при рендере (в презентере), а не синхронизируются через `useEffect` + `setState`.
- `useEffect` — только для синхронизации с внешним миром (таймеры, подписки); сеть — через `useQuery`, не через эффект.
- `key` в списках — стабильный идентификатор, не индекс.

## Комментарии

- **JSDoc (`/** … */`) — только в api-слое и контракте** (`src/api`, `src/types/api`, `shared/`, `server/tvmaze/`) и там, где пользователь явно попросил. В компонентах, хуках, `utils/`, константах, пропсах и доменных типах его нет (D-39).
- Вне api-слоя допустим только однострочный `//`, и только если он объясняет неочевидное **почему**: обходной путь, ограничение браузера или библиотеки, причину, которую не видно из кода. Исключение для общих SCSS-файлов — в `styles.md`.
- Запрещено: пересказ имени или кода («Genre filter + paging»), примеры вывода («"2 shows for …"»), ссылки на Figma/hw1. Причина: в маленьких файлах такой комментарий дублирует код в 1–5 строках под ним, устаревает при правке и засоряет файл.

```ts
// ❌
/** "2 shows for “murder”" (Figma: Results heading). */
export function formatResultsTitle(count: number, term: string) { … }

// ✅ src/ShowsExplorer/MainContent/Results/useResults.ts
// Focus to the heading first: a ‹ › button that turns disabled would drop it to <body>.
```

## Тесты

- Vitest, файл `name.test.ts` рядом с кодом: одна функция — один файл теста. Тестируем чистые функции, хуки (`renderHook`), таски (`tasks.md`) и сервер (`backend.md`). View не тестируем: в нём нет логики.
- В тесте проверяется поведение (вход → выход), а не детали реализации.
