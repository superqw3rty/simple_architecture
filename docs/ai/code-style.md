# Стиль кода

## Лимит 120 строк

Любой файл в `src/` — не больше 120 строк кода (пустые строки и комментарии не считаются). Для TS/TSX это проверяет ESLint (`max-lines`), для SCSS — `pnpm check:arch`. Ориентир для хорошего файла — около 70 строк.

Зачем: файл должен читаться как оглавление книги — набор понятных абстракций, детали которых спрятаны в соседних файлах.

Когда файл растёт, **не сжимай** код (однострочники, короткие имена, удаление пустых строк), а раздели по смыслу:

| Что разрослось | Как делить |
|---|---|
| View | выдели блок JSX в дочерний компонент `Child/` в папке родителя |
| Презентер | выдели связанную группу состояния и эффектов в хук `useSomething.ts` |
| Хук | выдели чистые вычисления в функцию `doSomething.ts` |
| Чистая функция / модуль | раздели по ответственности, общий тип — в `types.ts` |
| SCSS | это сигнал, что view пора делить на дочерние компоненты |
| Тест | раздели по тестируемым сценариям: `name.cache.test.ts` |

Делить нужно по смысловым границам, а не «первые 100 строк / остальное». У каждого нового файла должно быть имя, объясняющее его содержимое без открытия.

## Форматирование

- Форматирует Prettier (`.prettierrc.json`): одинарные кавычки, ширина 100, висячие запятые. Руками формат не правим: `pnpm format`. `pnpm check` падает на неотформатированном коде.
- **Тело `if` / `else` / `for` / `while` всегда в фигурных скобках и на отдельной строке**, даже если это одна инструкция (ESLint `curly: all`, чинится `eslint --fix`).

```ts
// ❌
if (value !== undefined) search.set(name, String(value));

// ✅
if (value !== undefined) {
  search.set(name, String(value));
}
```

Скобки не дают потерять вторую строку при правке, а лимит в 120 строк не повод их экономить — повод разделить файл.

## Именование

- Компоненты и их папки — `PascalCase`; хуки — `useCamelCase`; функции и переменные — `camelCase`; константы модуля — `UPPER_SNAKE_CASE`.
- Файл называется так же, как его главный экспорт: `paginate.ts` → `paginate`.
- Булевы — `is*`, `has*`, `can*`, `should*`. Обработчики в пропсах — `on*`, внутри презентера — `handle*`.
- Пропсы компонента — интерфейс `ComponentNameProps` в файле view (или в `types.ts`, если нужен презентеру).
- Без сокращений: `button`, `event`, `index`, а не `btn`, `e`, `i` (исключение — общепринятые `id`, `url`, `dto`).

## TypeScript

- `strict` + `noUncheckedIndexedAccess`. Без `any`; `unknown` + сужение типа. `as` — только на границе с внешним миром (ответ сервера, DOM).
- Импорт типов — `import type { ... }` / `import { type X }`.
- Состояния с вариантами — дискриминируемые объединения, а не набор независимых булевых флагов.
- **У каждой функции явный возвращаемый тип**: презентеры, хуки, `utils/`, `api/`, хелперы в тестах; ничего не возвращает — `: void`. Параметры — с типом (это уже требует `strict`). Без аннотации — только функция, тип которой задан контекстом: колбэк-аргумент (`items.map((item) => …)`, `it('…', () => …)`), значение типизированной переменной или свойства (`const Name: FC<NameProps> = …`, обработчик в объекте с объявленным типом результата). Проверяет ESLint (`explicit-function-return-type`), D-40.
- Результат хука — `interface UseNameResult` в файле хука; нужен ещё кому-то — в `types.ts` папки.
- Почему: выведенный тип виден только человеку при наведении, в коде его нет. Явный тип — контракт: правка реализации, которая его ломает, даёт ошибку в самой функции, а не у потребителей вдали от места правки.

```ts
// ❌
export function useShowsExplorer() { … }

// ✅
interface UseShowsExplorerResult {
  isCompact: boolean;
  query: string;
  term: string;
  onQueryChange: (query: string) => void;
}

export function useShowsExplorer(): UseShowsExplorerResult { … }
```
- Только именованные экспорты.

## React

- Только функциональные компоненты, объявление через стрелку с типом `FC`: `export const Name: FC<NameProps> = (props) => …` (D-28). Хуки и обычные функции объявляются как удобно.
- Производные данные вычисляются при рендере (в презентере), а не синхронизируются через `useEffect` + `setState`.
- `useEffect` — только для синхронизации с внешним миром (таймеры, подписки); сеть — через `useQuery`, не через эффект.
- `key` в списках — стабильный идентификатор, не индекс.

## SCSS

- Стили компонента — `ComponentName.module.scss` рядом с view, классы в `camelCase`: `styles.cardTitle`.
- Цвета, отступы, радиусы, шрифты, тени, длительности — только через CSS-переменные из `src/styles/tokens.scss` (`var(--color-accent)`). «Магических» значений в модулях нет.
- Из SCSS используем вложенность (не глубже 3 уровней), `&`-модификаторы и миксины для медиа-запросов. Переменные темы — CSS-переменные, не `$scss`.
- Варианты и состояния — `data-`/`aria-`атрибуты (`data-variant="ghost"`, `aria-pressed`), стили цепляются за атрибут: `&[data-variant='ghost']`. `className` во view — на усмотрение автора: один класс модуля, склейка нескольких (в том числе глобального `container`) или выбор класса тернарником допустимы (D-29). Инлайн-стили `style={{}}` — только для значений, приходящих из данных.
- Компонент не задаёт себе внешние отступы (`margin`) — расположением управляет родитель. Центрирование тоже: `margin: 0 auto` у компонента запрещён, родитель центрирует через flex/grid (`justify-content`, `align-items`), при необходимости — обёрткой в своём JSX (D-33).
- Mobile-first, базовая проверка на ширине 375px. Анимации уважают `prefers-reduced-motion`.

### Отступы и размеры

- Шкала отступов — сетка 4px, номер шага = значение / 4: `--space-1` (4) · `2` (8) · `3` (12) · `4` (16) · `5` (20) · `6` (24) · `8` (32) · `12` (48) · `16` (64) · `20` (80) · `30` (120). Это зеркало переменных Figma `space/*` (коллекция `Tokens`), в Figma у каждой указан code syntax `var(--space-N)`.
- `padding`, `margin`, `gap` — только `var(--space-*)` или `0`. Сырые `px`/`rem` в этих свойствах запрещены.
- В макете значение вне шкалы (например 10 или 22) — не заводи токен, а приведи к сетке и в Figma, и в коде. Новый шаг добавляется, только если он кратен 4 и нужен макету; имя — по тому же правилу (`--space-10` = 40px), старые имена не перенумеровываются.
- Размер элемента (точка логотипа, постер, иконка) — отдельный токен-размер (`--logo-dot-size`, `--poster-width-default`), а не `--space-*` или `--radius-*`, даже если число совпадает.
- **Кратны 4** (D-35, D-46): отступы, шрифты, высоты строк, скругления, высоты контролов. Исключения — толщина обводки (`border` 1–2px) и `--radius-pill`. Значение вне сетки в макете округляется до ближайшего кратного 4, при равном расстоянии — вверх (14 → 16, 30 → 32), и в Figma, и в коде. `pnpm check:arch` проверяет, что каждый длинный токен в `tokens.scss` кратен 4, а шаг `--space-N` / `--text-N` / `--leading-N` равен N × 4px.
- **Размеры элементов — любые** (D-46): ширины и высоты блоков, постер, точка логотипа, иконки, максимальные ширины, заглушки скелетона (`<Skeleton width={90} />`), а также всё, что получается из раскладки (`%`, `fr`, `flex`, по содержимому). Сетку держат значения, из которых раскладка складывается: отступы и типографика. `pnpm check:arch` не проверяет кратность у токенов-размеров (`--*-size`, `--*-width`, `--*-height`, кроме `--control-height-*`).
- Высота контрола (кнопка, чип, поле) задаётся токеном `--control-height-*` (`xs` 36 · `sm` 44 · `md` 52) при `box-sizing: border-box`, а не суммой `padding` + строка + рамка: рамка 1px иначе сдвигает высоту с сетки.
- В Figma обводка входит в раскладку (`strokesIncludedInLayout`), а в CSS `border` идёт снаружи `padding`: отступ в макете = `padding` в коде, рамка 1px добавляется сверху в обоих местах одинаково.

Почему: номер = значение / 4 — по числу из макета сразу видно токен, а вставка нового шага не ломает старые имена. Одна шкала в Figma и в коде делает расхождения видимыми на ревью.

```scss
// ❌
.field { padding: 0 22px; gap: 14px; }
.dot { width: var(--radius-sm); }

// ✅
.field { padding: 0 var(--space-5); gap: var(--space-3); }
.dot { width: var(--logo-dot-size); }
```

### Высота строки

- Размер шрифта — только `var(--text-N)`, номер шага = значение / 4, как у отступов: `--text-3` (12) · `4` (16) · `5` (20) · `8` (32) · `10` (40) · `11` (44) · `18` (72) · `19` (76).
- `line-height` — только `var(--leading-N)` по тому же правилу: `--leading-4` (16) · `6` (24) · `7` (28) · `8` (32) · `10` (40) · `12` (48) · `13` (52) · `18` (72) · `21` (84). Сырые числа, `px`, `em` и `%` запрещены (проверяет `pnpm check:arch`).
- **Каждый блок, где задан `font-size`, задаёт и `line-height`** — в том же селекторе или в том же миксине брейкпоинта (проверяет `pnpm check:arch`). Обычные пары: 12/16, 16/24, 20/28, 32/40, 40/48, 44/52, 76/84; другая пара — если так в макете (логотип 20/24, описание hero 20/32).
- В Figma высота строки задаётся в px той же парой; новый шаг шкалы добавляется, только если он кратен 4 и нужен макету.

Почему: высота строки в px — единственный способ держать каждую строку на сетке 4px (коэффициент 1.2 даёт 33.6px). Готовая длина наследуется как есть, и вложенный текст другого размера получил бы чужую высоту строки — поэтому `font-size` без `line-height` запрещён: каждый текст задаёт обе величины сам.

```scss
// ❌ коэффициент: 28 × 1.2 = 33.6px; шрифт без высоты строки
.title { font-size: 1.75rem; line-height: 1.2; }
.hint { font-size: var(--text-4); }

// ✅
.title { font-size: var(--text-8); line-height: var(--leading-10); }
.hint { font-size: var(--text-4); line-height: var(--leading-6); }
```

### Брейкпоинты

- Брейкпоинты задаются только в `src/styles/breakpoints.scss` (карта `$breakpoints`, сейчас `tablet: 768px`, `desktop: 1200px`, `wide: 1440px`; значение — ширина, с которой начинается экран). Миксины подключаются во все SCSS-модули автоматически через `additionalData` в `vite.config.ts`, поэтому писать `@use` вручную не нужно. Исключение — partial-файлы из `src/styles/`, подключённые через `@use` (например, `tokens.scss`): `additionalData` до них не доходит, там `@use './breakpoints' as *` пишется явно.
- Медиа-запросы по ширине пишутся в модуле компонента только через миксины:
  - `@include screen-from(tablet)` — `tablet` и шире (планшет + десктоп), основной инструмент;
  - `@include screen-below(tablet)` — уже `tablet`, то есть только мобильный;
  - `@include screen-between(tablet, desktop)` — от `tablet` включительно до `desktop` не включительно; нужен, когда значение разное на трёх диапазонах.
- Базовые стили без миксина — только то, что одинаково на всех экранах. Значение, которое на экранах разное, задаётся в непересекающихся миксинах: мобильное — в `screen-below`, десктопное — в `screen-from`, без значения в базе. Три разных значения — `screen-below(tablet)` + `screen-between(tablet, desktop)` + `screen-from(desktop)`, без перебивания `screen-from(tablet)` через `screen-from(desktop)`. Так CSS одного экрана не попадает в другой и не перебивается там.
- Число колонок сетки с пагинацией — делитель размера страницы, чтобы каждая полная страница заканчивалась полным рядом. Сейчас страница — 3 шоу, значит колонок 1 или 3; задаются брейкпоинтами (`screen-below(desktop)` / `screen-from(desktop)`), а не `auto-fill`, который сам выбирает 2.
- Когда у компонента в Figma несколько размерных вариантов, а диапазоны вариантов несмежные, миксины вариантов лежат в partial `_variants.scss` в папке компонента (пример — `ShowCard/_variants.scss`: `card-compact`, `card-default`). Модули компонента и его дочерних компонентов подключают его через `@use '<путь>/variants' as *`. Внутри partial — только миксины поверх `screen-*`, сырых `@media` нет.
- Значение, одинаково адаптивное в нескольких компонентах (боковой отступ страницы `--page-gutter`), — семантический токен в `tokens.scss`, переопределённый в миксинах; компоненты используют его без медиа-запросов.
- Сырые `@media (min-width/max-width/width …)` в модулях запрещены, это проверяет `pnpm check:arch`.
- Адаптивное значение берётся из шкалы токенов (`--text-8` → `--text-11`). Не хватает шага — добавь его в `tokens.scss`, а не магическое число в модуль. Семантический токен (`--text-brand`) заводится, только когда одно и то же адаптивное значение нужно в двух и более компонентах.
- Новый брейкпоинт добавляется в карту, когда он реально понадобился, а не «на будущее».

Почему: CSS-переменные не работают в условии `@media`, поэтому брейкпоинты хранятся в SCSS. Значения собраны в одном месте, а поведение компонента видно в его собственных стилях, без похода в токены. Непересекающиеся диапазоны означают, что каждое объявление действует ровно на своём экране: в десктопе нет мёртвых мобильных значений, которые перебиваются ниже.

```scss
// ❌ сырой медиа-запрос
.logo {
  font-size: 16px;
  @media (min-width: 768px) { font-size: 20px; }
}

// ❌ мобильное значение в базе, на десктопе перебивается
.logo {
  font-size: var(--text-4);
  line-height: var(--leading-6);
  @include screen-from(tablet) { font-size: var(--text-5); line-height: var(--leading-7); }
}

// ✅
.logo {
  font-family: var(--font-display); // одинаково везде — в базе
  @include screen-below(tablet) { font-size: var(--text-4); line-height: var(--leading-6); }
  @include screen-from(tablet) { font-size: var(--text-5); line-height: var(--leading-7); }
}

// ❌ стиль только для мобильного, который потом сбрасывается
.hint { display: block; @include screen-from(tablet) { display: none; } }

// ✅
.hint { @include screen-below(tablet) { display: block; } }
```

## Комментарии и тесты

- **JSDoc (`/** … */`) — только в api-слое** (`src/api`, `src/types/api`) и там, где пользователь явно попросил. В компонентах, хуках, `utils/`, константах, пропсах и доменных типах его нет (D-39).
- Вне api-слоя допустим только однострочный `//`, и только если он объясняет неочевидное **почему**: обходной путь, ограничение браузера или библиотеки, причину, которую не видно из кода.
- Запрещено: пересказ имени или кода («Genre filter + paging»), примеры вывода («"2 shows for …"»), ссылки на Figma/hw1. Причина: в маленьких файлах такой комментарий дублирует код в 1–5 строках под ним, устаревает при правке и засоряет файл.

  ```ts
  // ❌
  /** "2 shows for “murder”" (Figma: Results heading). */
  export function formatResultsTitle(count: number, term: string) { … }

  // ✅
  // Wrapped: refetch must not receive the click event as its options.
  onRetry: () => void refetch(),
  ```
- Тесты — Vitest, файл `name.test.ts` рядом с кодом. Тестируем чистые функции и хуки (`renderHook`). View не тестируем: в нём нет логики.
- В тесте проверяется поведение (вход → выход), а не детали реализации.
