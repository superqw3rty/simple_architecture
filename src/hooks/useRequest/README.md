# useRequest

Хук для загрузки данных с сервера: кэш на всё приложение, отмена запросов, защита от гонок, статусы. Написан вместо `useQuery` из TanStack Query и намеренно повторяет его контракт (см. «Переезд» в `docs/ai/data-fetching.md`).

## Быстрый пример

```ts
const { data, error, status, isFetching, refetch } = useRequest({
  key: ['shows', 'search', term],
  fn: ({ signal }) => searchShows(term, signal),
  enabled: term.length > 0,
  staleTime: 5 * 60_000,
});
```

Фичи не вызывают `useRequest` из презентера напрямую — только через свой хук-обёртку (`useShowsSearch`).

## Параметры

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `key` | `readonly unknown[]` | — | Идентификатор запроса. Запросы с одинаковым ключом считаются одним и тем же запросом и делят кэш. В ключе должно быть **всё**, от чего зависит ответ. Сравнивается по `JSON.stringify`, поэтому новый массив на каждом рендере — это нормально |
| `fn` | `({ signal }) => Promise<T>` | — | Функция, которая делает запрос. `signal` нужно пробросить в API-функцию, иначе отмена не сработает. Можно передавать новую функцию на каждом рендере — это не вызывает повторный запрос |
| `enabled` | `boolean` | `true` | `false` — запрос не отправляется. Используется, когда входных данных ещё нет (пустая строка поиска) |
| `staleTime` | `number` (мс) | `0` | Сколько времени данные из кэша считаются свежими и отдаются без похода в сеть |

## Результат

| Поле | Тип | Описание |
|---|---|---|
| `data` | `T \| undefined` | Последние успешно загруженные данные для текущего ключа |
| `error` | `Error \| null` | Ошибка последней попытки. Обычно `ApiError` с понятным `message` |
| `status` | `'idle' \| 'pending' \| 'success' \| 'error'` | Состояние данных (см. ниже) |
| `isFetching` | `boolean` | Прямо сейчас идёт сетевой запрос — и первая загрузка, и фоновое обновление |
| `refetch` | `() => void` | Запросить заново, игнорируя `staleTime`. Для кнопки «Try again» |

### Статусы

| `status` | Что это значит | Что показывать |
|---|---|---|
| `idle` | `enabled: false` и в кэше ничего нет | начальный экран |
| `pending` | данных ещё нет, идёт первая загрузка | скелетоны |
| `success` | данные есть (`data` определено) | список; если `isFetching` — можно показать ненавязчивый индикатор |
| `error` | последняя попытка упала, данных нет | сообщение `error.message` и кнопку с `refetch` |

```
          enabled: false
   ┌──────── idle ◀───────┐
   │ enabled: true        │
   ▼                      │
pending ──ошибка──▶ error ─┤ refetch / смена key
   │                  ▲   │
   │ успех            │   │
   ▼                  │   │
success ──данные устарели, фоновый запрос (isFetching: true)──▶ success | error
```

## Что происходит при вызове

1. Ключ превращается в строку (`serializeKey`).
2. Компонент подписывается на запись кэша с этим ключом через `useSyncExternalStore` — любое изменение записи перерисовывает всех подписчиков.
3. После рендера, если `enabled`, вызывается `fetchEntry`:
   - запрос с таким ключом **уже летит** → ничего не делаем, ждём его ответа (дедупликация);
   - в кэше есть **свежие** данные (моложе `staleTime`) → ничего не делаем;
   - иначе создаётся `AbortController`, запись помечается `isFetching: true`, вызывается `fn`.
4. Ответ записывается в кэш, **только если этот запрос всё ещё актуален** для ключа. Ответ отменённого или вытесненного запроса отбрасывается.

## Поведение в типичных ситуациях

- **Сменился `key`** (пользователь допечатал запрос). Компонент отписывается от старого ключа; если он был последним подписчиком, старый сетевой запрос отменяется через `AbortController`. Для нового ключа всё начинается с шага 2.
- **Компонент размонтирован во время загрузки.** То же самое: запрос отменяется, незавершённая запись удаляется из кэша.
- **Два компонента с одним ключом.** Один сетевой запрос, оба получают результат. Запрос отменится, только когда отпишутся оба.
- **Повторный запрос с тем же ключом.** Свежие данные (`staleTime` не истёк) отдаются мгновенно без сети. Устаревшие данные показываются сразу (`status: 'success'`), а в фоне идёт обновление (`isFetching: true`).
- **Ошибка.** `status: 'error'`, `data: undefined`. Следующее монтирование с этим ключом или `refetch()` пробует снова.
- **React StrictMode** (двойной запуск эффектов в dev). Первый запрос отменяется, второй доходит — в Network видно один отменённый и один успешный запрос. Это ожидаемо.

## Кэш

Кэш — обычный `Map` на уровне модуля (`requestCache.ts`), один на всё приложение. Провайдер не нужен.

- Живёт до перезагрузки страницы, в `localStorage` не пишется.
- Хранит до 50 записей; при переполнении удаляются самые давние записи, на которые никто не подписан.
- `invalidate(['shows'])` помечает устаревшими все записи, чей ключ начинается с `['shows', ...]` — следующий подписчик перезапросит данные.
- `clearCache()` отменяет все запросы и очищает кэш. Нужен в тестах: `beforeEach(() => clearCache())`.

## Файлы

| Файл | Ответственность |
|---|---|
| `useRequest.ts` | сам хук: подписка на кэш, запуск загрузки, сборка результата |
| `fetchEntry.ts` | решение «идти ли в сеть» и запись ответа: дедупликация, `staleTime`, защита от гонок |
| `requestCache.ts` | хранилище: записи, подписчики, вытеснение, отмена брошенных запросов, `invalidate` |
| `types.ts` | типы параметров, результата и записи кэша |
| `index.ts` | публичный API: `useRequest`, `invalidate`, `clearCache`, типы |
| `useRequest.test.ts` | сценарии: idle, успех, отмена и гонка, ошибка и повтор, кэш, фоновое обновление, дедупликация |

## Ограничения

Чего здесь нет по сравнению с TanStack Query: мутаций, автоматических повторов, refetch по фокусу окна и по интервалу, серверной пагинации, сохранения предыдущих данных при смене ключа, devtools. Если что-то из этого понадобилось — это сигнал к переезду, а не к доработке хука (`docs/ai/dependencies.md`, раздел «Кандидаты»).
